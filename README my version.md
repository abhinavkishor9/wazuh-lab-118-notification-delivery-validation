# wazuh-lab-118-notification-delivery-validation
## Overview
Wazuh notification delivery validation means verifying whether a security alert generated by Wazuh can travel through the configured notification mechanism and reach its intended destination.

The key idea is that generating an alert does not automatically mean a notification was delivered.

A Wazuh deployment may generate alerts successfully while notifications fail because of:
- Incorrect integration settings
- Authentication errors
- Network connectivity issues
- Destination-side rejection
- Delivery configuration problems

### Understand the Notification Flow

1. **Event occurs:** A monitored endpoint produces an event.
2. **Wazuh processes the event:** The event is analyzed and may trigger a rule.
3. **Alert is generated:** An alert is recorded in Wazuh.
4. **Notification mechanism processes it:** Configured email or an external integration handles the alert.
5. **Destination receives notification:** Delivery is confirmed using destination-side evidence.

This is a conceptual flow. The exact steps depend on the notification mechanism configured in your Wazuh environment.

### Three Outcomes You Must Distinguish

| Outcome | What It Proves |
|---|---|
| Alert generated | Wazuh detected an event and created an alert. |
| Delivery attempted | The configured notification mechanism attempted to send it. |
| Notification received | The intended destination actually received the notification. |

A successful command or a log stating that a message was submitted may demonstrate an attempt or acceptance by an intermediate service, but it does not necessarily prove that the recipient received it.


This lab examines the notification-delivery validation process in a Wazuh-based SOC environment. The objective is to distinguish between an endpoint event being generated, a corresponding alert being indexed, a notification being attempted, and the intended destination confirming receipt.

A Wazuh alert appearing in the index does not independently prove that an email or integration notification was sent or received.

## Lab Objectives

- Validate whether Wazuh detects controlled file modifications within an existing realtime-monitored directory.
- Examine the resulting File Integrity Monitoring (FIM) events and identify the integrity attributes reported as changed.
- Correlate endpoint activity with indexed Wazuh alerts using agent identifiers, timestamps, and file paths.
- Investigate discrepancies between events visible in the dashboard and results returned by exact-field searches.
- Review manager logs to identify indexer initialization warnings and agent synchronization issues that may affect investigation workflows.
- Distinguish alert generation and indexing from notification eligibility, send attempts, and confirmed destination receipt.
- Document verification gaps and classify the outcome using evidence-based criteria without assuming successful or failed notification delivery.

## Lab Scenario

A SOC analyst is validating whether a controlled file-integrity event on a Windows endpoint can be traced through Wazuh's alerting workflow and whether the available evidence supports confirming notification delivery.

The endpoint `DESKTOP-9MMM37V`, registered as agent `001`, has a File Integrity Monitoring (FIM) configuration that includes `C:\FIM-Lab` with realtime monitoring enabled. During the initial test, file creation failed because the configured directory did not exist locally. After the directory was made available, the analyst created and modified `lab118-notification-test.txt` to generate a controlled file-integrity event.

Wazuh subsequently displayed an integrity-change event for the test file. The event reported changes to the file's size, modification time, MD5, SHA-1, and SHA-256 attributes. However, searches filtering on the exact `syscheck.path` value returned no results, despite the event being visible in the dashboard. This discrepancy required further investigation rather than an assumption that the event had not been recorded.

During the investigation, manager logs also showed indexer initialization warnings and failed synchronization attempts for agent `001`, followed by successful initialization messages for several inventory indices. Although these messages provided useful operational context, the evidence did not establish that the warnings caused the query discrepancy or affected notification delivery.

The analyst must determine how far the event can be traced through the notification workflow using the available evidence.

The investigation focuses on:
- Confirming the controlled FIM event and correlating it with indexed alert data.
- Investigating the mismatch between the dashboard event and exact-path search results.
- Reviewing manager and indexer logs for relevant operational issues.
- Establishing whether a notification mechanism is configured and whether the test alert qualifies for notification.
- Seeking evidence of a notification attempt and receipt at the intended destination.

The scenario ends with an evidence-based assessment. The FIM integrity-change event was observed, but notification configuration, delivery attempts, and destination receipt were not verified. Therefore, successful end-to-end notification delivery cannot be claimed, and the overall result remains **Inconclusive**.

## Environment

- **SIEM / Endpoint Security:** Wazuh
- **Endpoint OS:** Windows
- **Endpoint hostname:** `DESKTOP-9MMM37V`
- **Wazuh agent ID:** `001`
- **Agent IP shown in the event:** `192.168.203.1`
- **Alert index:** `wazuh-alerts-4.x-2026.10.26`
- **Monitored directory:** `C:\FIM-Lab`
- **Test file:** `C:\FIM-Lab\lab118-notification-test.txt`
- **FIM monitoring mode:** Realtime

## Procedure

1. Inspect the Windows agent configuration and identify existing FIM directories.
2. Confirm that `C:\FIM-Lab` exists.
3. Create or modify the controlled test file.
4. Inspect recent Wazuh alerts and identify the matching FIM event.
5. Search for the event using agent ID, timestamp, and file path.
6. Investigate query mismatches and manager/indexer warnings.
7. Review the configured notification mechanism and its eligibility conditions, if administrative access is available.
8. Check delivery records and verify receipt at the intended destination.
9. Record the final result based only on available evidence.

## Key Findings

- The agent configuration contained a `C:\FIM-Lab` directory entry with realtime monitoring enabled.
- The first attempt to create the test file failed because the directory did not exist locally.
- After the directory was made available, the test file was created and subsequently modified.
- A Wazuh event showed the test file being modified in realtime mode.
- The event reported changes to size, modification time, MD5, SHA-1, and SHA-256 attributes.
- The event description was `Integrity checksum changed.`
- Exact-path searches against `syscheck.path` returned zero hits, despite the event visible in the dashboard.
- Manager logs showed indexer initialization warnings and failed agent synchronization attempts, followed by successful initialization messages for several inventory indices.
- No evidence was collected that confirms successful notification delivery to an intended destination.

## Result

**Overall outcome: Inconclusive**

The FIM detection stage was demonstrated by the recorded integrity-change event. The end-to-end notification-delivery objective was not completed because notification configuration, send status, and destination receipt were not established.

This result does not mean notification delivery failed. It means the available evidence is insufficient to confirm success or failure.

## Limitations

- Notification settings were not confirmed.
- The intended notification destination was not established.
- Notification send attempts and destination-side receipt were not verified.
- The discrepancy between the visible event and exact-path search results remains unresolved.
- Indexer warnings were observed, but their direct relationship to the query mismatch or notification delivery was not established.
